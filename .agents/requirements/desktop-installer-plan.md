# 桌面安装器计划

更新：2026-10-25。对应 [完整编号清单](development-checklist.md) 的 `02.04`、`02.06`、`02.09` 与 [进展概览](../TODO.md) 的「官方版并存与桌面交付」。新安装器设计仅为计划；当前用户已授权现有 Windows x64 安装器的本机构建与升级，不签名、不发布。

## 交付矩阵

优先级固定为 Windows x64 Desktop → Linux x64 Desktop → macOS ARM Desktop → Android＋PRoot Fedora。当前只执行 Windows 安装交付；其余平台与新安装器设计均处于计划阶段。Android 草案与验收项见 [追加需求](2026-10-25-followups.md#平台交付矩阵计划)。

## 目标

- 交付一个能在用户机器上**安装、启动、升级、卸载**的 Windows 桌面安装包，并与官方 DeepSeek Harness 同机并存、数据不串。
- 每一阶段留下可复核的证据；证据缺失的阶段不算完成，也不许用 Web 页面替代桌面验收。
- 打包、签名、上传、发布是四个不同动作，本计划默认停在「本机可安装」，越界需要单独授权。

## 本轮本机交付

源码 8c1bc7cae6 的 v0.1.0 已在原安装目录覆盖安装并两次启动；107 个会话、设置与配置文件安装前后相同，官方 EXE 未改变。此次只验收手动安装更新，未验收下载更新、签名、卸载回滚或全新电脑。

## 现状（2026-10-25）

- **身份已分离**：`appId` 为 `com.deepseek.dsh.uncensored`、产品名 `DeepSeek Harness Uncensored`、协议 `dshu://`、CLI `dsh-uncensored`、数据目录 `.dsh-uncensored`；官方版是 `com.deepseek.dsh` / `DeepSeek Harness` / `.dsh`，因此两者在注册表、安装目录、数据目录、协议与 CLI 上互不覆盖。
- **可产出未签名包**：`pnpm run package:desktop:win:x64:unsigned` 已跑通，产物为 `apps/desktop/.desktop-build/targets/win-x64/unsigned-artifacts/runs/<构建批次>/deepseek-harness-uncensored-0.1.0-win-x64-unsigned.exe`；未签名产物带 `-unsigned` 后缀，与发行产物不可能混淆。
- **安装器只支持按用户安装**：NSIS 脚本 `installer.nsh` 在检测到全用户安装（`${isForAllUsers}`）或 `HKLM` 下已有 `InstallLocation` 时直接提示并以退出码 2 结束；安装目录固定为 `%LOCALAPPDATA%\Programs\DeepSeek Harness Uncensored`。
- **未签名构建不写更新配置**：未签名产物没有 `app-update.yml`，因此本阶段没有自动更新通道。
- **卸载保留 Harness home**：uninstall.nsh 明确保留会话所在的 Harness home；清理的是 Electron 用户资料与 updater 缓存。升级及 /KEEP_APP_DATA 跳过该清理；不能把缓存清理写成删除全部会话。
- **版本已解耦**：产品版本 `0.1.0` 与 DSH 引擎 `0.2.1-rc.2` 分别写入 runtime 描述与发行校验，引擎版本变化不再要求产品版本同步。

## 阶段

### 阶段 0 — 工具链与预检

- 现状：`desktop-toolchain-preflight.ts` 与 `prepare-windows-installer.ps1` 通过 `vswhere` 检查 Visual C++ 工具；本机装的是 VS 18 Insiders，两处查询已加 `-prerelease`，此前「缺少 Visual Studio C++ 工具」的阻塞已解除。
- 动作：每次打包前先跑 `--check`，把预检失败当作构建前置失败处理，不在编译期才暴露。
- 验收：预检通过后进入编译；预检失败时构建目录保持干净且不产生半成品安装包。
- 证据：预检输出与 `.desktop-build/packaging-runs/<run>/result.json`。

### 阶段 1 — 未签名安装包在本机可用

- 动作：打出未签名安装包，备份既有安装目录后静默安装（`/S`），核对注册表卸载项、开始菜单与桌面快捷方式、`dshu://` 协议注册、CLI 链接与托盘图标。
- 验收：安装后首次启动不闪退；重启系统后仍可从快捷方式启动；`dsh-uncensored --version` 与安装版一致；卸载项能完整移除程序与快捷方式。
- 证据：安装目录清单、HKCU 卸载项导出、启动日志、卸载后的目录快照。
- 停止条件：安装器要求管理员权限、或与官方版共用注册表键时立即停止并回到本计划。

### 阶段 2 — 与官方版并存

- 动作：官方版与本项目同时安装、同时运行，分别登录、创建会话、装插件、改设置；交叉重启两版。
- 验收：两版进程互不终止；两版数据目录、凭据、插件、会话、浏览器资料互不读写；`dshu://` 只唤起本项目，官方协议的唤起不受影响；任一版卸载后另一版仍可启动。
- 证据：两版并存时的目录快照、会话列表对照、重启后的登录态截图。
- 注意：官方版的插件与顶部入口曾被本分支误改，本阶段只观测不修复官方版配置。

### 阶段 3 — 升级

- 动作：用同一安装器覆盖安装更高版本，观察运行中替换、替换后首次启动与设置读取。
- 验收：覆盖安装保留用户数据与设置；替换期间应用正确退出并重新拉起；低版本安装包不能覆盖高版本。
- 证据：两次安装的版本号与数据目录对照、替换过程日志。
- 依赖：未签名构建没有更新通道，升级只能手动触发安装包；自动更新留到阶段 5。

### 阶段 4 — 签名

- 动作：按 [Windows 签名与运行器操作](../../apps/desktop/windows-signing/README.zh.md) 配置证书、签名工具、密钥容器与 Token，先跑签名预检，再出签名包。
- 验收：签名与时间戳齐全，Windows 信任链校验通过，`app-update.yml` 中的 `publisherName` 由证书身份派生；未签名产物不得进入发布通道。
- 证据：签名批次记录、信任校验输出、发布者身份与证书的一致性记录。
- 阻塞：本分支没有可用的 EV 证书与 Token，签名阶段的实际完成需要单独授权与硬件操作。

### 阶段 5 — 发布与自动更新

- 动作：配置发布通道与产物上传，使安装版能发现并安装新版本。
- 验收：更新提示按补丁／次版本／主版本分级；下载失败或离线时保留旧版本继续可用；被拒绝的版本不会替换已安装版本。
- 证据：更新检查响应、下载与替换日志、拒绝路径的记录。
- 停止条件：发布与上传未经单独授权时，本阶段不启动。

### 阶段 6 — 卸载与数据处置

- 动作：分别验证「保留数据」与「彻底清理」两种卸载结果，确认会话、凭据、插件与缓存的最终去向。
- 验收：卸载后程序、快捷方式、协议注册、CLI 链接全部消失；用户数据要么按选择保留，要么按选择清除，不留半截状态。
- 证据：卸载前后目录与注册表对照。

## 待决策

- **并存形态**：是否只支持与官方版并存的按用户安装，还是也要提供全用户安装？现有脚本对全用户安装直接退出，扩展需要单独的设计与权限评估。
- **签名通道**：自签证书只够本机可信，公开分发需要真实发行身份，两者不能混用。
- **卸载数据**：当前清理 Electron 资料及更新缓存、保留 Harness home；是否提供显式彻底清理入口仍待决定。
- **更新通道**：Nightly、固定版本还是仅手动安装，决定 `app-update.yml` 与发布脚本的配置方式。

## 不做的事

- 不修改官方版 DSH 的安装、配置、插件或文件；官方版只作为并存对照出现。
- 不上传、不发布、不自动更新，除非单独授权。
- 不用 Web 页面或源码启动器替代桌面安装验收。
- 不把「打包成功」当作「安装可用」，两者之间的每一步都要留证据。
