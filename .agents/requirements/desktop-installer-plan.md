# 桌面安装器计划

更新：2026-11-11。对应 [完整编号清单](development-checklist.md) 的 `02.04`、`02.06`、`02.09` 及 [02.11](2026-11-01-upstream-installer.md#0211-安装器明确属于独立-dshu)。Windows 现有安装器继续完善，Linux x64 正在适配与验收。全新安装器架构和 Android 草案仍为计划。

## 交付矩阵

优先级固定为 Windows x64 Desktop → Linux x64 Desktop → macOS ARM Desktop → Android＋PRoot Fedora。Windows 已完成多轮本机检查版交付。Linux 已完成干净源码打包与 Ubuntu WSL2 的 deb 验收。macOS 和 Android 尚未完成桌面发行验收。Android 草案与验收项见 [追加需求](2026-10-25-followups.md#平台交付矩阵)。

## 目标

- 交付一个能在用户机器上**安装、启动、升级、卸载**的 Windows 桌面安装包，并与官方 DeepSeek Harness 同机并存、数据不串。
- 每一阶段留下可复核的证据；证据缺失的阶段不算完成，也不许用 Web 页面替代桌面验收。
- 打包、签名、上传、发布是四个不同动作，本计划默认停在「本机可安装」，越界需要单独授权。

## 本轮本机交付

Windows 已安装检查版 `0.1.0-test.20261111.6`，源码 `1408c12cc1`，产品版本 0.1.0、内核 DSH 0.2.2-rc.1、内置 REA 6.8.0。原位升级后重新打开，7,266 个用户文件及官方版 EXE/ASAR 哈希一致。系统安装目录通过四模式、新建会话及命令执行测试，独立卸载项版本一致。实际安装器解包通过桌面侧栏和三个浏览器的 HTTPS 正反例、终端代理及 SSH 回环。此前已验证同内核检查包回退与再升级。跨数据格式回退、系统重启、签名更新与全新电脑仍待验收。产物、备份与验证记录见 [HANDOFF](../HANDOFF.md)。

现有原生安装界面中英文各 16 项通过，涵盖路径、安装、启动选择、失败重试、运行进程拒绝及卸载。实际交互在 200% 桌面缩放下完成；进度渲染器分别在 96/192 DPI、浅深色下检查。测试使用独立产品身份与目录，未覆盖所有物理显示器组合。

## 现状（2026-11-10）

- **身份已分离**：`appId` 为 `com.deepseek.dsh.uncensored`、产品名 `DeepSeek Harness Uncensored`、协议 `dshu://`、CLI `dsh-uncensored`、数据目录 `.dsh-uncensored`；官方版是 `com.deepseek.dsh` / `DeepSeek Harness` / `.dsh`，因此两者在注册表、安装目录、数据目录、协议与 CLI 上互不覆盖。
- **可产出未签名包**：`pnpm run package:desktop:win:x64:unsigned` 已跑通。产物按构建批次隔离，验证后另存 `.dsh-build/deliverables` 并保留源码节点、构建编号和摘要；未签名构建不作为正式发行包。
- **安装器只支持按用户安装**：NSIS 脚本拒绝全用户安装；默认目录为 `%LOCALAPPDATA%\Programs\DeepSeek Harness Uncensored`，允许选择其他有效目录，拒绝磁盘根目录及未登记的非空目录。
- **未签名构建不写更新配置**：未签名产物没有 `app-update.yml`，因此本阶段没有自动更新通道。
- **卸载保留用户资料**：普通和静默卸载均保留 Electron 用户资料、Harness home 和更新缓存。显式传入 `/DELETE_APP_DATA=1` 可清理 Electron 资料及更新缓存，升级参数优先保留。对仍使用旧卸载器的安装，保留数据的卸载参数为 `/S /KEEP_APP_DATA`。
- **版本已解耦**：产品版本 `0.1.0` 与 DSH 引擎 `0.2.2-rc.1` 分别写入 runtime 描述与发行校验，引擎版本变化不要求产品版本同步。同日检查包需同时核对源码节点，构建编号不保证源码唯一。

## 阶段

### Linux x64 检查阶段

- 干净源码 `4b1e436740` 的标准流水线生成未签名 deb/tar.gz。Ubuntu WSL2 安装目录通过四模式、REA、Office 和 CLI 检查，tar.gz 中的 ASAR 与实装摘要一致。
- `.2` 原位升级到 `.3` 后保留 92 个隔离资料文件，使用同一份资料重新打开。Xvfb 中实际窗口的 `WM_CLASS` 与已安装桌面入口的 `StartupWMClass` 一致。
- `.3` 卸载后保留 96 个隔离资料文件，应用和启动链接已移除。随后直接运行带空格路径中解压的 tar.gz，工作区、命令菜单和关于页通过。Xvfb 的窗口类及 Weston 原生 Wayland 的应用标识均为 `deepseek-harness-uncensored`。物理桌面、门户集成、其他发行版及正式发行仍待验收。产物和摘要见 [HANDOFF](../HANDOFF.md)。
- `.4` 的 deb 已在 Debian 12 隔离根文件系统验收。先移除 ALSA 和 GBM，再由 APT 从 deb 声明解析并安装两项依赖。原生 X11 窗口、关于页与命令菜单通过，卸载保留 87 个隔离资料文件。chroot 的用户命名空间受限，真实桌面沙箱另行验收。
- `.5` 由 `1408c12cc1` 干净打包。deb 和 tar.gz 中的 ASAR 摘要一致，deb 保留 ALSA 与 GBM 声明。在 Ubuntu WSL2 从含空格的便携路径启动，X11 窗口、关于页及三个实包浏览器的 HTTPS 正反例通过。
- 同一 `.5` 便携包通过 Ubuntu WSL2 的 Wayland 目录门户检查。真实门户前端搭配可控后端验证选择、取消、重试及并发请求合并。Ubuntu 自带 GTK 后端通过原生选择器打开检查。实包渲染进程启用 Seccomp 和 `NoNewPrivs`。Headless Weston 无键鼠席位，实体桌面的父窗口模态与输入仍待验收。见[交接记录](../HANDOFF.md#linux-wayland-目录门户与渲染沙箱2026-11-11)。

### 阶段 0 — 工具链与预检

- 现状：`desktop-toolchain-preflight.ts` 与 `prepare-windows-installer.ps1` 通过 `vswhere` 检查 Visual C++ 工具；本机装的是 VS 18 Insiders，两处查询已加 `-prerelease`，此前「缺少 Visual Studio C++ 工具」的阻塞已解除。
- 本机 Spectre 组件已通过 UAC 补装，退出码 0、无需重启；打包进程使用 `VCToolsVersion=14.52.36629` 与 `MSVCPreviewEnabled=true`，未改变全局默认工具集。完整新包构建通过，证据见 HANDOFF。
- 动作：每次打包前先跑 `--check`，把预检失败当作构建前置失败处理，不在编译期才暴露。
- 验收：预检通过后进入编译；预检失败时构建目录保持干净且不产生半成品安装包。
- 证据：预检输出与 `.desktop-build/packaging-runs/<run>/result.json`。

### 阶段 1 — 未签名安装包在本机可用

- 动作：打出未签名安装包，备份既有安装目录后静默安装（`/S`），核对注册表卸载项、开始菜单与桌面快捷方式、`dshu://` 协议注册、CLI 链接与托盘图标。
- 验收：安装后首次启动不闪退；重启系统后仍可从快捷方式启动；`dsh-uncensored --version` 与安装版一致；卸载项能完整移除程序与快捷方式。
- 证据：安装目录清单、HKCU 卸载项导出、启动日志、卸载后的目录快照。
- 停止条件：安装器要求管理员权限、或与官方版共用注册表键时立即停止并回到本计划。

### 阶段 2 — 与官方版并存

- 动作：官方版与本项目同时安装、同时运行，分别登录、创建会话、装插件、改设置；交叉重启两版。
- 验收：两版进程互不终止；两版数据目录、凭据、插件、会话、浏览器资料互不读写；`dshu://` 只唤起本项目，官方协议的唤起不受影响；任一版卸载后另一版仍可启动。
- 证据：两版并存时的目录快照、会话列表对照、重启后的登录态截图。
- 注意：官方版的插件与顶部入口曾被本分支误改，本阶段只观测不修复官方版配置。

### 阶段 3 — 升级

- 已验收：本机同内核检查包的保留数据卸载、旧包回退、旧版运行及最新包原位升级，证据 `.dsh-build/rollback-cycle-20261106-result.json`。未验证跨 Session/数据库格式降级，也未据此认定低版本覆盖拦截通过。
- 动作：用同一安装器覆盖安装更高版本，观察运行中替换、替换后首次启动与设置读取。
- 验收：覆盖安装保留用户数据与设置；替换期间应用正确退出并重新拉起；低版本安装包不能覆盖高版本。
- 证据：两次安装的版本号与数据目录对照、替换过程日志。
- 依赖：未签名构建没有更新通道，升级只能手动触发安装包；自动更新留到阶段 5。

### 阶段 4 — 签名

- 动作：按 [Windows 签名与运行器操作](../../apps/desktop/windows-signing/README.zh.md) 配置证书、签名工具、密钥容器与 Token，先跑签名预检，再出签名包。
- 验收：签名与时间戳齐全，Windows 信任链校验通过，`app-update.yml` 中的 `publisherName` 由证书身份派生；未签名产物不得进入发布通道。
- 证据：签名批次记录、信任校验输出、发布者身份与证书的一致性记录。
- 阻塞：本分支没有可用的 EV 证书与 Token，签名阶段的实际完成需要单独授权与硬件操作。

### 阶段 5 — 发布与自动更新

- 动作：配置发布通道与产物上传，使安装版能发现并安装新版本。
- 验收：更新提示按补丁／次版本／主版本分级；下载失败或离线时保留旧版本继续可用；被拒绝的版本不会替换已安装版本。
- 证据：更新检查响应、下载与替换日志、拒绝路径的记录。
- 停止条件：发布与上传未经单独授权时，本阶段不启动。

### 阶段 6 — 卸载与数据处置

- 已验收：实际 `/S /KEEP_APP_DATA` 卸载保留两处 DSHU 数据及官方 DSH 文件，之后旧包和新包均可安装运行。
- 动作：继续核对卸载后的快捷方式、协议和 CLI，并仅在隔离资料中验证显式清理 Electron 资料及更新缓存；不清理真实用户数据。
- 验收：程序入口按卸载结果移除；Harness home 与官方 home 始终保留，Electron 资料和更新缓存按明确选择处置。清理不跨越重解析点或受保护目录。
- 证据：卸载前后目录与注册表对照。

## 待决策

- **并存形态**：是否只支持与官方版并存的按用户安装，还是也要提供全用户安装？现有脚本对全用户安装直接退出，扩展需要单独的设计与权限评估。
- **签名通道**：自签证书只够本机可信，公开分发需要真实发行身份，两者不能混用。
- **卸载数据**：当前默认保留全部资料；显式清理只作用于 Electron 资料及更新缓存，Harness home 与官方 home 始终受保护。完整清理 Harness 数据不在现有卸载器范围。
- **更新通道**：Nightly、固定版本还是仅手动安装，决定 `app-update.yml` 与发布脚本的配置方式。

## 不做的事

- 不修改官方版 DSH 的安装、配置、插件或文件；官方版只作为并存对照出现。
- 不上传、不发布、不自动更新，除非单独授权。
- 不用 Web 页面或源码启动器替代桌面安装验收。
- 不把「打包成功」当作「安装可用」，两者之间的每一步都要留证据。
